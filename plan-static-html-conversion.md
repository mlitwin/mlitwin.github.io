# Plan: Convert to Simple Static HTML Site

## Overview

Replace Eleventy with the simplest possible pipeline:

1. **`build-lib`** — collects third-party CSS/JS (PicoCSS, KaTeX, Prism, heading-anchors) from `node_modules` into `lib/`. Reusable by any site.
2. **`assemble`** — copies `content/`, `lib/`, and `public/` into `_site/`. ~30 lines of Node.js; no templating.

There is no site build script. Pages are lean HTML files that use **Web Components** (`<site-nav>` / `<site-footer>`) for shared chrome. All dynamic rendering (math, heading anchors, syntax highlighting, site components) happens client-side at runtime. No tags pages, feed, or sitemap generated.

The Web Components pattern is a first-class goal: it proves out an approach that transfers directly to future sites.

## 1. Web Components: `<site-nav>` and `<site-footer>`

`public/js/site-components.js` defines both custom elements. It is a **site-authored file** (not from npm), so it lives in `public/` and is copied to `_site/` by the assemble step. The content is site-specific; the pattern is what transfers to future sites.

### No-flash loading rule

Load `site-components.js` with a **synchronous `<script>` in `<head>`** — no `defer`, no `async`. This registers the custom elements before the browser parses `<body>`, so `<site-nav>` and `<site-footer>` are already defined when the parser encounters them. They render immediately with no visible flash.

```html
<head>
  ...
  <script src="/js/site-components.js"></script>  <!-- synchronous: no defer, no async -->
</head>
```

### `public/js/site-components.js`

```js
class SiteNav extends HTMLElement {
  connectedCallback() {
    this.innerHTML = `
      <header class="container">
        <nav>
          <ul><li><strong><a href="/">Matthew Litwin</a></strong></li></ul>
          <ul>
            <li><a href="/blog.html">Blog</a></li>
            <li><a href="/resume.html">Resume</a></li>
          </ul>
        </nav>
      </header>`;
  }
}

class SiteFooter extends HTMLElement {
  connectedCallback() {
    this.innerHTML = `
      <footer class="container">
        <small>
          <a href="https://github.com/mlitwin">GitHub</a> ·
          <a href="https://www.linkedin.com/in/matthewlitwin/">LinkedIn</a>
        </small>
      </footer>`;
  }
}

customElements.define('site-nav',    SiteNav);
customElements.define('site-footer', SiteFooter);
```

**Why not Shadow DOM?** Pico's classless styles target elements by tag name and won't pierce shadow DOM. Light DOM keeps `<header>`, `<nav>`, `<footer>` fully styleable by `site.css` and Pico without any extra work.

**Reusability pattern:** Any future site copies `site-components.js`, swaps in its own nav/footer HTML, and gets the same zero-flash component chrome. The loading convention (`<script>` in `<head>`, synchronous) and the `connectedCallback`/`innerHTML` pattern are the transferable parts.

## 2. Authored Content Format

Pages are lean HTML files. The shared chrome is delegated to the Web Components; each page only authors what is unique to it.

### Post Template (`templates/post.html`) — Copy to Start a New Post

```html
<!DOCTYPE html>
<html lang="en" data-theme="auto">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Post Title – Matthew Litwin</title>
  <meta name="date" content="YYYY-MM-DD">
  <link rel="stylesheet" href="/lib/pico.min.css">
  <link rel="stylesheet" href="/lib/katex.min.css">
  <link rel="stylesheet" href="/lib/prism-okaidia.min.css">
  <link rel="stylesheet" href="/css/site.css">
  <script src="/js/site-components.js"></script>
</head>
<body>
  <site-nav></site-nav>

  <main class="container">
    <article>
      <header>
        <h1>Post Title</h1>
        <p><time datetime="YYYY-MM-DD">Month DD, YYYY</time></p>
      </header>

      <p>Content here.</p>

      <!-- Inline math: $v = x^i e_i$ -->
      <!-- Display math: $$g_{ij} x^i y^j$$ -->

      <!-- Code block: -->
      <pre><code class="language-python">def hello(): pass</code></pre>

      <!-- Images: author provides the file and writes the tag -->
      <!-- <img src="./diagram.svg" alt="Description"> -->

    </article>
  </main>

  <site-footer></site-footer>

  <script src="/lib/katex.min.js"></script>
  <script src="/lib/katex-auto-render.min.js"></script>
  <script src="/lib/heading-anchors.js"></script>
  <script src="/lib/prism.min.js"></script>
  <script>
    document.addEventListener("DOMContentLoaded", function () {
      renderMathInElement(document.body, {
        delimiters: [
          { left: "$$", right: "$$", display: true },
          { left: "$",  right: "$",  display: false }
        ]
      });
    });
  </script>
</body>
</html>
```

Compared to the all-inline version, each post file no longer contains the nav or footer HTML — those are ~12 lines gone from every file. The author edits only: `<title>`, `<meta name="date">`, `<h1>`, `<time>`, and the `<article>` body.

**Key conventions:**
- Math is raw LaTeX in `$...$` / `$$...$$`. KaTeX auto-render processes it at runtime.
- Code: standard `<pre><code class="language-X">`. Prism highlights at runtime.
- Heading anchors: `heading-anchors.js` attaches links to `<h2>`–`<h6>` at runtime.
- Images: author co-locates files with the post and writes `<img>` tags directly.
- Prev/next navigation: linked manually in the post when desired.

### Home / Blog Archive Pages

`index.html` and `blog.html` use `<site-nav>` and `<site-footer>` the same way. The post list is hand-maintained by the author — add a new `<li>` entry when a new post is published.

## 3. Library Build Step (`scripts/build-lib.js`)

Copies third-party assets from `node_modules` into `lib/`. `lib/` is not committed — regenerated on every build.

**What it copies:**

| Source (node_modules)                                          | Destination (lib/)           |
|:---------------------------------------------------------------|:-----------------------------|
| `@picocss/pico/css/pico.min.css`                              | `pico.min.css`               |
| `katex/dist/katex.min.css`                                    | `katex.min.css`              |
| `katex/dist/fonts/`                                           | `katex/` (fonts dir)         |
| `katex/dist/katex.min.js`                                     | `katex.min.js`               |
| `katex/dist/contrib/auto-render.min.js`                       | `katex-auto-render.min.js`   |
| `@zachleat/heading-anchors/heading-anchors.js`                | `heading-anchors.js`         |
| `prismjs/prism.js` (bundled via esbuild with language addons) | `prism.min.js`               |
| `prismjs/themes/prism-okaidia.css`                            | `prism-okaidia.min.css`      |

**npm packages to add:**
- `@picocss/pico`
- `katex`
- `@zachleat/heading-anchors`
- `prismjs`
- `esbuild` (minifies Prism + selected language grammars into one file)

~100 lines of `fs.cpSync` / `fs.copyFileSync` plus one esbuild call. No webpack, Rollup, or Vite.

**Reusability:** `lib/` contains only standard, path-agnostic files. Any site runs the same `build-lib.js` to produce an identical bundle. `site-components.js` is separate (in `public/js/`) because its content is site-specific.

## 4. Assemble Step (`scripts/assemble.js`)

Copies the three source trees into `_site/`. ~30 lines of Node.js:

```js
import { rmSync, mkdirSync, cpSync } from "fs";

rmSync("_site", { recursive: true, force: true });
mkdirSync("_site");
cpSync("content", "_site",        { recursive: true });
cpSync("lib",     "_site/lib",    { recursive: true });
cpSync("public",  "_site/public", { recursive: true });
```

No parsing, no generation, no template filling.

## 5. GitHub Actions Update

```yaml
# .github/workflows/gh-pages.yml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  pull_request:

jobs:
  deploy:
    runs-on: ubuntu-22.04
    permissions:
      contents: write
    concurrency:
      group: ${{ github.workflow }}-${{ github.ref }}
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'

      - run: npm ci

      - name: Build library bundle
        run: npm run build-lib

      - name: Assemble site
        run: npm run assemble

      - name: Deploy
        uses: peaceiris/actions-gh-pages@v3
        if: github.ref == 'refs/heads/main'
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./_site
```

**Changes from current workflow:**
- `actions/checkout@v3` → `@v4`, `setup-node@v3` → `@v4`
- `npm install` → `npm ci`; caching via built-in `setup-node` `cache: 'npm'`
- Drop the Eleventy `.cache` cache step
- Two steps: `build-lib` then `assemble` (replaces single `build-ghpages`)

### Migration tool (`scripts/migrate.js`)

One-time script that converts each markdown post to the new HTML format:

1. Parse YAML front matter (extract `title`, `date`)
2. Convert markdown body to HTML using `marked`
3. Wrap in the full post HTML shell from `templates/post.html` (with `<site-nav>`, `<site-footer>`, all `<script>` tags)
4. Write output as `index.html` alongside the original

```
node scripts/migrate.js content/blog/tensor-calculus/index.md
```

Markdown originals kept until verified, then deleted.

### Post-migration manual review checklist (per post):

- [ ] **LaTeX math**: `$...$` and `$$...$$` survive markdown conversion unchanged; verify KaTeX renders correctly (watch for `\` escaping, `$` in table cells)
- [ ] **Tables**: spot-check alignment; Pico styles `<table>` natively
- [ ] **Images**: verify `<img src="...">` paths match co-located assets
- [ ] **Code blocks**: confirm `<code class="language-X">` class is emitted; fix per-post if not
- [ ] **Inline HTML**: posts with raw HTML should pass through markdown-it untouched — verify no double-escaping
- [ ] **`<site-nav>` / `<site-footer>`**: load in browser and confirm no flash; check nav links are correct for the page's depth
- [ ] **Update `index.html` and `blog.html`**: add the new post entry manually

## 8. Styling Approach with PicoCSS

Pico styles semantic HTML directly — the `<header>`, `<nav>`, `<footer>`, `<article>`, `<table>` injected by the Web Components and post content are all styled automatically. The `public/css/site.css` override layer only needs to handle:

- Reading width (Pico's container is responsive; may want a max-width cap for long-form prose)
- Post metadata line — small/muted `<time>`
- Code block tweaks (Pico and Prism both style `<pre>` — likely needs one background override)
- Math display overflow scroll on narrow screens
- Dark mode is automatic via `data-theme="auto"` on `<html>` — no custom CSS needed
